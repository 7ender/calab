# ADR-0029: Комнаты «Только по списку» — скрыты и от администраторов (2026-09-27)

## Контекст
Владелец (docs/09 #46): убрать видимость приватной комнаты у всех, даже у админов, и дать доступ только конкретным людям. По ADR-0026 `ADMINISTRATOR` даёт «всегда полный доступ» и игнорирует переопределения — такую комнату сделать нельзя.

## Решение
1. **Флаг.** `rooms.restricted boolean NOT NULL DEFAULT false` (миграция 00024), `CHECK (NOT restricted OR is_private)`. Proto: `Room.restricted`, `UpdateRoomRequest.restricted` (optional).
2. **Кто меняет.** Только владелец пространства: `PATCH /api/rooms/{id} {restricted}` сверяет `workspaces.owner_id` с вызывающим (не бит); иначе `403 FORBIDDEN, reason OWNER_ONLY`. Непубличная комната обязательна (`422` для публичной). Остальные поля PATCH — по-прежнему `MANAGE_ROOM`.
3. **Правило `computePermissions`** (Go `perm.ComputeOrdered` / TS, новые входы `restricted`, `owner`):
   ```
   base = OR(roles[].permissions)
   if restricted:  owner → all;  иначе base &= ~ADMINISTRATOR   (обхода нет)
   elif base & ADMINISTRATOR → all
   дальше как раньше: переопределения ролей по position, персональное, без VIEW_ROOM → 0
   ```
   Админ (встроенный `admin` и любые роли с `ADMINISTRATOR`) считается обычным участником: без явного `allow VIEW_ROOM` (по роли или лично) комната для него не существует — список, чтение, отправка, голос и LiveKit-grant, участники «в голосе», упоминания, поиск, уведомления, файлы, запись, события gateway. С `allow` — права участника, которые дают переопределения (не «всё»). Владелец — полный доступ всегда.
4. **Владелец** = `workspaces.owner_id`. В правилах он узнаётся по встроенной роли `owner`: её держит только он (выдаётся при создании пространства, не назначается и не снимается, передачи владения нет); Go — `Member.Role == owner`, TS — роль с `builtin = OWNER`.
5. **Суперадмин продукта** обхода не имеет и не получает: это пользовательские данные; `/api/admin/*` показывает только счётчики комнат.
6. **Доступ** выдаётся существующими переопределениями комнаты (`allow VIEW_ROOM` людям и ролям) — новой таблицы нет. Переопределения правит тот, у кого в комнате `MANAGE_ROOM` (владелец; админ — только если владелец выдал ему `MANAGE_ROOM` в комнате, и тогда не шире своих битов в ней).
7. **Живое применение.** Смена флага → `ROOM_UPDATE` (+ `ROOM_PERMISSIONS_UPDATE` с теми же переопределениями, чтобы `rtc.SyncPublisher` пересчитал гранты звонка): gateway пересчитывает `VIEW_ROOM` → `ROOM_DELETE` потерявшим доступ (клиент выходит из звонка), `ROOM_CREATE` получившим; LiveKit — `UpdateParticipant`/`RemoveParticipant`. `sameVisibility` учитывает флаг.
8. **Снятие флага** — админы сразу снова видят комнату (`ROOM_CREATE`), переопределения не трогаются. **Перевод в публичную**: `is_private` через API не меняется; если это появится — `restricted` сбрасывается вместе с ним (CHECK). Удаление `deny VIEW_ROOM` у `member` при включённом флаге открывает комнату участникам — и админам как участникам.
9. **Порядок комнат** (`PUT …/rooms/order`, `MANAGE_ROOM` ws): комнату, которую действующий не видит, передать нельзя (`422 not found`), чтобы ответ не раскрывал её.

## Последствия
- Меняет ADR-0026 п. 2 («владелец/админ — без переопределений») для `restricted`-комнат; docs/04 и docs/16 помечены «изменено ADR-0029».
- Второе security-ревью обязательно (права). Общие векторы `proto/testdata/permissions.json` (`restricted`, `owner`).
- Модерация уровня пространства (серверный мьют, исключение, бан) по-прежнему работает на любого участника — она не раскрывает комнату.
