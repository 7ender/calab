# ADR-0026: Свои роли пространства (2026-09-27)

## Контекст
Владелец: создавать свои роли на уровне пространства, задавать им права и затем использовать роли в правах комнат и чатов. Сейчас (ADR-0008, docs/04): четыре фиксированные роли `owner|admin|member|guest`, одна на участника, `room_permissions` по `target_type role|user`, `computePermissions` — одна функция в Go и TS с общими тест-векторами.

## Решение
1. **Модель.** `workspace_roles(id, workspace_id, name ≤ 32, color, position, permissions bigint, builtin owner|admin|member|guest|NULL, mentionable, created_at)`; `member_roles(member_id, role_id)` — много ролей у участника. Встроенные роли создаются миграцией для каждого пространства: `owner` и `admin` (полный доступ, нельзя редактировать права/удалить), `member` (редактируемые права, роль по умолчанию для новых), `guest` (права гостя, редактируемые в рамках гостевого набора). Существующие `workspace_members.role` мигрируются в `member_roles`; поле остаётся как «старшая встроенная роль» для совместимости (owner/admin/member/guest) и обновляется при изменении ролей.
2. **Права.** Уровень пространства: `perms = OR(roles.permissions)`; владелец/админ → ALL. Уровень комнаты: базовые = права пространства → переопределения ролей по возрастанию `position` (allow/deny каждой роли участника, старшая роль последней) → персональное переопределение пользователя. Владелец/админ — без переопределений (полный доступ; **изменено ADR-0029**: в комнате `restricted` админ считается обычным участником, владелец — полный доступ). Это Discord-модель; реализуется в `computePermissions` (Go + TS, тест-векторы в `proto/testdata`), гранты LiveKit — из результата, как сейчас.
3. **Ограничения.** Роли создают/меняют участники с новым битом `MANAGE_ROLES` (у admin по умолчанию); нельзя выдать роль с правами выше своих (не-админ не может создать роль с `MANAGE_ROLES`/`MANAGE_WORKSPACE`); нельзя редактировать роли выше своей старшей; ≤ 50 ролей на пространство; удаление роли — с переносом участников (роль по умолчанию) и удалением её переопределений.
4. **API/события.** `GET/POST/PATCH/DELETE /api/workspaces/{id}/roles`, `PUT …/roles/order`, `PUT /api/workspaces/{id}/members/{uid}/roles {role_ids[]}`; события `ROLE_CREATE|UPDATE|DELETE`, `MEMBER_UPDATE` с `role_ids`; READY: `roles[]` пространства, `members[].role_ids`; `room_permissions.target_id` для ролей — `role_id` (uuid) вместо имени (миграция переводит старые `role:member|guest` цели на id встроенных). Proto — добавления; старое поле `role` остаётся.
5. **UI.** Настройки пространства → «Роли»: список с цветом и числом участников, перетаскивание порядка, создание/переименование/цвет, матрица прав (группы: Общие / Комнаты / Голос / Модерация), «Участники с ролью» с добавлением через `MemberPicker`; меню/профиль участника → «Роли ›» чекбоксы; права комнаты → цели: все роли пространства (владелец/админ read-only «полный доступ»); цвет имени и значок — по старшей роли (`RoleMark` для своих ролей — цветная точка).

## Последствия
- Миграция 00021 (роли, member_roles, перенос целей), новый бит `MANAGE_ROLES`, изменение `computePermissions` — второе независимое ревью обязательно; интеграционные тесты на матрицу прав.
- Клиенты старше 0.6.0 продолжают работать по полю `role` (старшая встроенная роль).
