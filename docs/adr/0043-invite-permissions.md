# ADR-0043: Права на приглашения — INVITE_MEMBERS и INVITE_GUESTS

**Статус:** принято (2026-09-30)
**Контекст:** владелец (30.09): «не хватает возможности дать на комнату и на пространство права приглашать мемберов и приглашать гостей (отдельными правами)». До этого приглашения в пространство проверялись `MANAGE_WORKSPACE`, гостевые ссылки комнат и решение по «стукам» гостей (ADR-0016, ADR-0040) — `MANAGE_ROOM`. Выдать «приглашать» без «управлять» было нельзя.

## Решение

1. **Два бита** (`permissions.proto`, `perm`, `PERMISSION_BITS`, никогда не переиспользуются):
   - `INVITE_MEMBERS = 1 << 21` — приглашения в пространство: ссылки-инвайты, email-приглашения, добавление аккаунта (`/api/workspaces/{id}/invites…`, `…/members`, вкладка «Приглашения»). В комнате — **ссылка только для участников** (`room_invites.members_only`, ниже).
   - `INVITE_GUESTS = 1 << 22` — гостевые ссылки комнаты (создать / список / отозвать / настройка подтверждения ссылки), решение по ожидающим гостям (REST, READY, маршрутизация событий в шлюзе), гостевые ссылки встреч от имени организатора (ADR-0038).
2. **Уровни.** Оба бита — на ролях (действуют во всех комнатах) и в переопределениях комнаты (`RoomOnly` / `ROOM_ONLY_PERMISSIONS` их включает; переопределения досок — нет). Приглашения в пространство проверяются по правам пространства (переопределения комнат на них не влияют); ссылки комнаты — по правам в комнате.
3. **Без импликации в `computePermissions`.** `MANAGE_WORKSPACE` не даёт `INVITE_MEMBERS`, `MANAGE_ROOM` не даёт `INVITE_GUESTS` — биты отзываются независимо. Чтобы при обновлении никто не потерял возможность, миграция 00047 выдала `INVITE_MEMBERS` всем ролям с `MANAGE_WORKSPACE`, `INVITE_GUESTS` — ролям с `MANAGE_ROOM`, и переопределениям комнат, где разрешён / запрещён `MANAGE_ROOM`, — такой же allow / deny `INVITE_GUESTS`. `ADMINISTRATOR` — по-прежнему всё. У `member` по умолчанию нет ни одного.
4. **Гости — никогда.** `GuestMax` их не содержит; обработчики отказывают гостю независимо от переопределений (ссылки — `linkAccess`, решения — `decider`, шлюз — роль ≠ guest; приглашения в пространство требуют подтверждённый не-гостевой аккаунт).
5. **Ссылка «только для участников»** (`room_invites.members_only`, `RoomInvite.members_only`, `CreateRoomInviteRequest.members_only`, превью `GetRoomInviteResponse.members_only`). Её создаёт `INVITE_MEMBERS` (или `INVITE_GUESTS`) в комнате; `allow_guests` у неё всегда false, настройки подтверждения нет. Вход по ней — только участник пространства (не гость): даёт ему доступ к комнате (личный override с битами ссылки, как раньше), иначе `403 reason INVITE_MEMBERS_ONLY`, никто не становится гостем. С одним `INVITE_MEMBERS` в комнате список ссылок показывает и отзывает только такие ссылки (остальные — 404). Это «пригласить участника в комнату» из диалога «Пригласить» (выбор участника → ссылка в личку).
6. **Клиент.** `mayInviteMembers` / `mayInviteGuests` (пространство), `mayInviteMembersIn` / `mayInviteGuestsIn` / `mayInviteToRoom` (комната). Настройки комнаты: вкладки «Основное / Медиа / Права» — `MANAGE_ROOM`, «Ссылка для гостей» — `INVITE_GUESTS` (переключатель подтверждения комнаты — `MANAGE_ROOM`). Редактор ролей — группа «Приглашения».

## Последствия

- Права применяются сразу, без перелогина: назначение роли (`WORKSPACE_MEMBER_UPDATE` с `role_ids`), правка битов роли (`ROLE_UPDATE`) и переопределения (`ROOM_PERMISSIONS_UPDATE`) доходят до сессий пользователя, стор клиента пересчитывает права на рендере, резолвер сервера инвалидируется (`TestInviteRightsApplyLive`, `dispatch.test.ts`).
- Кто получил `INVITE_GUESTS` на лету, увидит уже ожидающих гостей после переподключения (READY); новые «стуки» — сразу.
- Протокол: новые биты и поле `members_only` (старые клиенты его игнорируют; их ссылки — обычные гостевые).
