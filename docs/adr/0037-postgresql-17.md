# ADR-0037: PostgreSQL 17 поддерживается: полифилл `uuidv7()` (2026-09-28)

> Уточнение владельца 2026-10-01: PostgreSQL 17 и 18 остаются поддерживаемыми.
> CI и финальный полный интеграционный прогон выполняются только на PostgreSQL 17.
> Второй полный прогон на 18 не требуется; это заменяет прежнюю матрицу ниже.
> Уже обнаруженные ошибки на 18 не отменяются этим изменением процесса.

## Контекст
Все id генерирует Postgres встроенной `uuidv7()` (docs/04): `DEFAULT uuidv7()` у 19 столбцов в 12 миграциях и вызов в запросе `ClearDM` (`cleared_before`). Встроенная `uuidv7()` появилась только в PostgreSQL 18, поэтому на 17 падает уже первая миграция: `function uuidv7() does not exist`. Управляемые PostgreSQL у облачных провайдеров не всегда предлагают 18, а API должен работать и на 17. Порядок id значим: курсоры ленты, маркер прочтения (`GREATEST` по id), `cleared_before` и нижняя граница «с момента вступления» в `ListReadStates` сравнивают id как время. Других возможностей только из PG 18 в миграциях и запросах нет (grep по списку новинок 18; все 342 запроса sqlc проходят `PREPARE` на 17).

## Решение
- **До миграций сервер сам создаёт `public.uuidv7()`, если `uuidv7()` не резолвится** (`DB.Migrate`/`MigrateTo` — и при старте, и в `server migrate`; SQL — `apps/server/internal/db/uuidv7.sql`). Одновременный старт реплик: `pg_advisory_xact_lock`, повторная проверка после ожидания читает `pg_proc`, чтобы увидеть функцию, созданную соседней репликой (голый `to_regprocedure()` отвечает из устаревшего кеша каталога). База, где `uuidv7()` уже есть, не меняется.
- **Функция повторяет встроенную PG 18** (RFC 9562, метод 3): 48 бит Unix-мс, версия 7, 12 бит доли миллисекунды в `rand_a` из микросекунд `clock_timestamp()`, вариант `10`, остальные биты — случайные байты `gen_random_uuid()`. Как и в 18, id одной сессии строго растут: вызов в ту же 1/4096 мс или после шага часов назад берёт предыдущее значение + 1 (сессионная настройка `calaba.uuidv7_tick`). PL/pgSQL, `PARALLEL UNSAFE` (`set_config` запрещён в параллельных воркерах). Суперпользователь не нужен — только `CREATE` в схеме `public`, как и для самих миграций (с PG 15 это право по умолчанию только у владельца базы).
- **На 18 ничего не создаётся**: встроенная `pg_catalog.uuidv7()` резолвится всегда, `pg_catalog` просматривается раньше `public`.
- **Почему не миграция.** Функция нужна раньше `00001`, а новую миграцию раньше неё goose не применит (версии идут по порядку). Правка уже применённой `00001` переписала бы историю: сработала бы только для новых баз и потребовала бы ветвления по версии сервера внутри миграции и её Down. Наличие `uuidv7()` — свойство сервера БД, а не схемы, как версия Valkey, которую сервер проверяет при старте (ADR-0017). Базе, перенесённой с 18 на 17 дампом, функция нужна независимо от истории миграций.

## Последствия
- Поддерживаются PostgreSQL 17 и 18; интеграционные тесты в CI идут на обоих (матрица `go-integration`: нога 18 сохраняет имя обязательной проверки «go integration tests», нога 17 — «go integration tests (PostgreSQL 17)»). Ниже 17 не проверяется. *Уточнение 2026-09-30 (время CI):* на 17 — только на тегах `v*` и `workflow_dispatch` (каждый релиз проверен на обоих), на push/PR — только 18; «go integration tests» — сводный джоб над шардами.
- На 18 поведение не меняется. На 17 вызов стоит ~4 мкс против ~1 мкс у встроенной (100 000 вызовов: 420 мс против 92 мс) — на фоне INSERT незаметно.
- Точность часов на 17 — микросекунда (`clock_timestamp()`), у PG 18 на Linux — наносекунды: id разных сессий внутри одной микросекунды на 17 упорядочены произвольно. Порядок внутри сессии и между сессиями по времени сохраняется (`TestUUIDv7Polyfill`).
- Обновление 17 → 18 (`pg_upgrade` или дамп): `public.uuidv7()` остаётся, привязанные к ней DEFAULT продолжают работать, запросы без схемы берут встроенную; id у обеих совместимы (PG 18 читает время полифилла через `uuid_extract_timestamp()`, id вперемешку сортируются по времени). Убрать полифилл можно позже миграцией (`SET DEFAULT pg_catalog.uuidv7()` и `DROP FUNCTION`), это не обязательно.
- Перенос базы 18 → 17 дампом требует шага руками: `pg_dump` пишет `DEFAULT uuidv7()` без схемы при пустом `search_path` (рецепт — docs/06, «Резервные копии»).
- Сервер создаёт функцию, только если её нет, поэтому новое тело функции доставляется миграцией с `CREATE OR REPLACE`.
