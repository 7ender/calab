# 0047 — Кнопки под сообщениями ботов

Статус: принято, 2026-09-30. Дополняет ADR-0031.

## Решение

Обычное сообщение бота может содержать `inline_keyboard`: до 5 строк по 5 кнопок.
Кнопка содержит уникальный `id` (1–64 ASCII буквы, цифры, `_`, `-`), `label` (1–80
символов без управляющих), непрозрачный `data` (до 512 байт) и `disabled`.
`allowed_user_ids` (до 50 UUID, пусто = любой с правами) ограничивает всю клавиатуру.
Все поля видны читателям сообщения: секреты в `data` запрещены. Пользовательские
сообщения, системные карточки и стикеры не получают кнопки; пересылка копирует только
содержимое, без активной клавиатуры. Старые клиенты продолжают показывать текст.

`PATCH /api/messages/{id}` заменяет клавиатуру целиком; пустая удаляет её, отсутствие
поля сохраняет. `preserve_content: true` оставляет текст и требует переданную клавиатуру
и пустой `content`. Без флага прежняя семантика текста неизменна, включая пустой текст.
Сервер увеличивает `keyboard_revision` при любой правке текста или клавиатуры.

Человек отправляет `button_id`, `keyboard_revision`, `nonce` в
`POST /api/messages/{id}/interactions`. Сервер блокирует строку сообщения, проверяет
живую версию, кнопку, разрешённого пользователя, VIEW_ROOM и SEND_MESSAGES через
новый resolver (включая task rooms), доступ активного бота, блокировку и границу
очищенного DM. Для DM требуется общее пространство, как при отправке ботом.
Актор и `data` берутся из авторизации и БД, не из запроса.

Квитанция `interaction_id` и запись существующего `bot_webhook_deliveries` создаются
в одной транзакции, если webhook включён. Никакой новой очереди. `BOT_CALLBACK`
уходит только на user channel бота-автора; workspace fan-out и повторная постановка
через webhook-декоратор исключены. Одинаковый `(user_id, nonce)` возвращает прежнюю
квитанцию без второй доставки, даже после правки/удаления клавиатуры. Другая кнопка,
версия или сообщение с тем же nonce дают 409. Повтор всё ещё требует текущего доступа,
живого сообщения и доступного бота. Квитанции хранятся до физического удаления сообщения.

## Гарантии и ответственность бота

200 подтверждает принятие, не исполнение действия. Webhook использует существующие
подпись, ретраи и предел суток; может прийти повторно. Gateway публикуется после
коммита, best effort: RESUME помогает только в рамках живой сессии/буфера. При сбое
между commit и publish или новом IDENTIFY событие может потеряться; REST истории его
не восстанавливает. Для важных действий нужен webhook. Retry принятого nonce не
пытается повторить gateway-доставку. `BotCallback.id` одинаков в обоих транспортах.

Бот обязан сохранять дедупликацию `id`, проверять актуальную версию своего доменного
объекта и полномочия автора, а внешний эффект выполнять с идемпотентным ключом.
Принятое перед правкой callback не отменяется правкой сообщения. Две разные nonce
не считаются одним намерением; exactly-once внешний эффект Calab не гарантирует.
Код приватных ботов, интеграции и бизнес-логика сюда не входят.

## Интерфейс

Memo-компонент под сообщением держит pending/error локально. После принятия вся
клавиатура заблокирована до новой версии от бота. При сетевом повторе nonce тот же;
при 409 клиент один раз загружает актуальное сообщение, без автоматического нажатия
новой кнопки. Есть явное обновление при неудаче загрузки. Поддерживаются клавиатура,
aria-live и мобильные цели от 44 px. Автоматических сообщений в чат нет.
