# ADR-0040: Подтверждение входа гостей («зал ожидания») (2026-09-29)

## Контекст
Владелец: в настройках комнаты — пускать гостей по ссылке сразу или требовать подтверждения; то же
можно задать и на отдельной ссылке. Когда ссылка требует подтверждения, человек заходит в комнату и
видит «ожидаем подтверждения организатора», а у организатора внутри комнаты появляется группа с теми,
кого нужно подтвердить: их можно переименовать, задать бейдж и пустить/отклонить. Встречи календаря
(ADR-0038) выдают внешним гостевые ссылки — они наследуют настройку комнаты.

## Решение
1. **Настройка.** `rooms.guest_approval bool NOT NULL DEFAULT false` (настройки комнаты, `MANAGE_ROOM`);
   `room_invites.require_approval bool NULL` — `NULL` наследует комнату, `true/false` переопределяют для
   этой ссылки (поле в диалоге ссылки: «Как у комнаты / Сразу / С подтверждением»). Гостевые ссылки
   встреч (ADR-0038) создаются с `NULL`.
2. **Модель.** `room_admissions (room_id, user_id, invite_id, status pending|admitted|declined,
   requested_at, decided_by NULL, decided_at NULL, PRIMARY KEY (room_id, user_id))`. Переход по ссылке
   с подтверждением (сценарии ADR-0016 b/c; участник комнаты (а) подтверждения не проходит) создаёт
   гостя/членство `guest` **без** override на комнату и строку `pending`. Пока `pending`, гость не видит
   комнату (ADR-0008: роль `guest` не видит ничего) — READY отдаёт ему `pending_admissions[] {room_id,
   room_name, workspace_id, workspace_name, requested_at}`, и клиент показывает экран ожидания вместо
   комнаты. `admitted` → пишется override как в ADR-0016 (биты ссылки), гость получает комнату обычным
   `ROOM_CREATE`/снапшотом; `declined` → строка остаётся 10 мин (повторный стук не раньше), членство
   гостя в пространстве снимается, если у него нет других комнат. `pending` без решения 30 мин →
   `declined` автоматически (метёлка раз в 30 с), гость видит «Никто не ответил» и может постучать снова.
3. **Кто решает.** `MANAGE_ROOM` в комнате и автор ссылки (организатор встречи). Им — событие
   `ROOM_ADMISSION_REQUEST {room_id, user, invite_id, requested_at}` (тост «<Имя> просит войти в
   <комната>» со звуком уведомления и кнопками «Пустить/Отклонить», счётчик на строке комнаты), при
   решении всем решающим — `ROOM_ADMISSION_DECIDED {room_id, user_id, status, decided_by}`; гостю —
   `ROOM_ADMISSION_DECIDED` по `user:<id>`.
4. **API.** `GET /api/rooms/{id}/admissions` (pending, решающим), `POST /api/rooms/{id}/admissions/{user_id}
   {status: admitted|declined, display_name?, badge_id?}` — имя пишется в `users.display_name` гостя
   (гость локален для пространства), бейдж — в `workspace_members.badge_id` (ADR бейджей, docs/09 #82);
   `DELETE /api/rooms/{id}/admissions/me` — гость отменяет ожидание. `PATCH /api/rooms/{id}` получает
   `guest_approval`; `POST/PATCH /api/rooms/{id}/invites` — `require_approval`. Боты — только `GET`.
5. **Клиент.** Панель участников в комнате: группа «Ожидают подтверждения (N)» над остальными — строка
   гостя с полем имени (inline, Enter сохраняет), пикером бейджа (иконка), кнопками «Пустить» / «Отклонить»;
   строка комнаты в сайдбаре — счётчик ожидающих (как непрочитанные, но иконкой «стук»). Экран ожидания
   гостя: название комнаты и пространства, «Ожидаем подтверждения организатора…», лоадер (единственная
   разрешённая бесконечная анимация), «Отменить»; после решения — вход в комнату или «Организатор
   отклонил вход» / «Никто не ответил» с кнопкой «Постучать снова». Мобильный веб — те же экраны.
6. **Права и лимиты.** Решение проверяется на сервере (`MANAGE_ROOM` или `invite.created_by`); гость не
   получает LiveKit-токен и историю, пока не `admitted`; `pending` на комнату ≤ 50 (дальше 429); стук
   ограничен rate-limit гостей по IP (ADR-0016); имя ≤ 40, бейдж — из библиотеки пространства.
