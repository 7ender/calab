# ADR-0048. Ролевая модель v2: права по функциям и закрытые разделы

Статус: принято (2026-09-30), к релизу **1.3.0**. Владелец, 30.09: «надо прям ролевую модель улучшить —
больше контроля над доступами хочу, возможно прятать от админов доски, давай различные права более
тонко по функциям приложения». Развивает ADR-0008 (биты), ADR-0026 (несколько ролей), ADR-0043
(раздельные права без импликации от `MANAGE_*`).

## Контекст

Сегодня `MANAGE_WORKSPACE` — «всё административное»: создание досок, записи, боты, баны, SIP,
настройки, приглашения (до ADR-0043). А `ADMINISTRATOR` видит всё, включая приватные комнаты и
доски. Для команды из нескольких отделов это плохо: руководитель продаж, ведущий свои доски и
временные комнаты с клиентами, не хочет, чтобы их видел системный админ, а HR не должен иметь
право менять ботов ради того, чтобы банить. Нужны права по функциям и разделы, закрытые даже от
администраторов.

## Решение

### 1. Новые биты (уровень пространства, если не сказано иначе)
| Бит | Значение | Что даёт | Сегодня это |
|---|---|---|---|
| `CREATE_BOARDS` | 1 << 25 | создавать доски (управление своей доской — `MANAGE_BOARD` через override создателя, как у временных комнат) | `MANAGE_WORKSPACE` |
| `MANAGE_MEMBERS` | 1 << 26 | кик, бан/разбан, бейджи, подтверждение заявок, смена чужих ролей ниже своей (в паре с `MANAGE_ROLES` для правки самих ролей) | `MANAGE_WORKSPACE` |
| `MANAGE_BOTS` | 1 << 27 | создавать/править/удалять ботов пространства, их права | `MANAGE_WORKSPACE` |
| `MANAGE_INTEGRATIONS` | 1 << 28 | SIP (ADR-0046), GPTunneL, вебхуки, будущие интеграции | `MANAGE_WORKSPACE` |
| `VIEW_JOURNALS` | 1 << 29 | журнал звонков, активность досок, аудит пространства (аналитика) | `MANAGE_WORKSPACE`/`MANAGE_BOARD` |
| `MANAGE_EVENTS` | 1 << 30 | править/отменять чужие встречи, встречи «на всю комнату», напоминания всем | организатор / `MANAGE_WORKSPACE` |
| `MANAGE_RECORDINGS` | 1 << 31 | удалять/скачивать записи любой комнаты; своей — как раньше | `MANAGE_WORKSPACE` |

`MANAGE_WORKSPACE` остаётся: название/иконка/тема, тариф, политика гостей, опасная зона, всё, что не
вынесено. **Миграция `00052`** выдаёт все семь новых битов каждой роли, у которой есть
`MANAGE_WORKSPACE` (никто ничего не теряет), участнику по умолчанию — ни одного. `ADMINISTRATOR`
по-прежнему включает все биты. Импликаций «`MANAGE_*` ⇒ новый бит» в `computePermissions` нет
(правило ADR-0043): каждый бит снимается отдельно.

### 2. Закрытые разделы («закрытая» доска и комната)
- `rooms.restricted bool`, `boards.restricted bool` (миграция `00052`). Закрытый объект видят и
  входят в него **только** те, у кого есть личный или ролевой override `VIEW_ROOM`/`VIEW_BOARD` на
  него, плюс создатель (override ставится при создании) и **владелец пространства**.
  `ADMINISTRATOR` и `MANAGE_WORKSPACE`/`MANAGE_BOARD`/`MANAGE_ROOM` на уровне пространства
  **не открывают** закрытый объект: в `computePermissions` для `scope.restricted = true` бит
  `ADMINISTRATOR` не разворачивается в «всё», а действует как обычная роль без override; бит
  `VIEW_*` берётся только из override. Владелец — единственное исключение (он отвечает за данные и
  биллинг и не может быть заперт снаружи своего пространства).
- Закрытый ⊃ приватный: включить «закрытая» можно только у приватной; в диалоге «Доступ» это
  третий уровень переключателя «Все участники / По списку / По списку, без администраторов» с
  пояснением «Администраторы пространства не видят раздел; владелец видит всегда».
- Списки, поиск, упоминания, уведомления, календарь (встреча с `room_id` закрытой комнаты),
  задачи в ленте (карточка задачи закрытой доски), экспорт, боты — везде фильтр по тому же
  резолверу; для закрытых объектов чужим — 404, не 403 (не раскрываем существование).
- Кто может закрыть: `MANAGE_ROOM`/`MANAGE_BOARD` на объекте (включая создателя временной комнаты
  и создателя доски). Открыть обратно — те же, а также владелец.
- Записи закрытой комнаты, файлы, транскрипты — под тем же резолвером; `MANAGE_RECORDINGS` на
  закрытую комнату не действует без override.

### 3. Редактор ролей
Группы: «Пространство» (`MANAGE_WORKSPACE`, `MANAGE_ROLES`, `MANAGE_STICKERS`), «Участники»
(`MANAGE_MEMBERS`, `MANAGE_NICKNAMES`), «Приглашения» (ADR-0043), «Комнаты» (`MANAGE_ROOM`,
`CREATE_TEMP_ROOMS`, `VIEW_ROOM`…), «Голос» (…), «Модерация» (`MANAGE_MESSAGES`, `MUTE_MEMBERS`,
`MOVE_MEMBERS`), «Календарь» (`MANAGE_EVENTS`), «Доски» (`CREATE_BOARDS`, `VIEW_BOARD`,
`CREATE_TASKS`, `EDIT_TASKS`, `MANAGE_BOARD`), «Записи» (`MANAGE_RECORDINGS`, `STREAM`, `VIDEO`),
«Телефония» (`PLACE_CALLS`), «Интеграции и боты» (`MANAGE_BOTS`, `MANAGE_INTEGRATIONS`), «Журналы»
(`VIEW_JOURNALS`). У каждого бита подсказка одной строкой «что даёт / кому по умолчанию».
Шаблоны ролей при создании: «Модератор», «Менеджер отдела» (CREATE_BOARDS, CREATE_TEMP_ROOMS,
INVITE_GUESTS, MANAGE_EVENTS, VIEW_JOURNALS), «Наблюдатель» (только просмотр, без SEND).
Предпросмотр «Что увидит участник с этой ролью»: список разделов (комнаты, доски, настройки),
считается тем же `computePermissions` на клиенте.

### 4. Совместимость и безопасность
- Иерархия ADR-0026 сохраняется: выдать/снять бит можно только ниже своей высшей роли; никто, кроме
  владельца, не может дать `ADMINISTRATOR`.
- Все проверки на сервере, единый резолвер (`internal/perm`) — точка, где `restricted` меняет
  семантику `ADMINISTRATOR`; тест-векторы `proto/testdata` для: админ vs закрытая комната без
  override, админ с override, владелец, участник по override, гость (никогда), бот с override.
- Клиент только прячет UI; после смены прав — как сейчас (`WORKSPACE_MEMBER_UPDATE`, `ROLE_UPDATE`,
  `ROOM_PERMISSIONS_UPDATE`), плюс новое `BOARD_PERMISSIONS_UPDATE`, если его ещё нет.
- Второе ревью обязательно (права + протокол).

## Последствия
- Миграция `00052`; `computePermissions` в TS и Go с новым полем scope `restricted`;
  `botAllow`-таблица пересматривается по новым битам; docs/16 матрица переписывается.
- Отклонено: убрать `ADMINISTRATOR` вовсе (ломает все существующие пространства); «закрыть от
  владельца» (владелец отвечает за данные); отдельная сущность «отдел/команда» с правами (Slack-
  подобные группы) — возможно позже поверх ролей, не вместо.
