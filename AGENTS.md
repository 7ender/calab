# Repository instructions

Before starting work in this repository, read and follow [CLAUDE.md](CLAUDE.md).
It contains the shared project instructions for all coding agents, including the
required documentation, architecture constraints, and review and testing rules.

## Codex delegation

When the lead session runs in Codex, use only Codex for delegated agents and
reviews. Do not launch Claude agents from Codex. This owner instruction overrides
the Claude-specific model and role assignments in CLAUDE.md; the other project
rules, including isolated worktrees, still apply.

For coding agents, prefer the latest available SOL model (currently
`gpt-6.1-sol`) unless the owner specifies another model.

## Рабочий процесс Codex (решение владельца, 2026-10-01)

Эти правила уточняют CLAUDE.md для работы из Codex и имеют приоритет над его старыми
назначениями Fable/Opus/Sonnet/GLM. Источники процесса: CLAUDE.md,
[архитектурные решения](docs/adr/README.md), [тестирование](TESTING.md),
[релизный runbook](docs/06-deployment.md), [сопровождение](docs/11-maintenance.md).
Исторические результаты тестов и старые релизные команды не являются текущим evidence.

### Лид отвечает за архитектуру и результат

- Лид сам изучает код и ограничения, принимает архитектурные решения, пишет ADR и
  конкретную спецификацию **до запуска зависимой реализации**. Исследовательские
  предложения агентов — входные данные, а не разрешение агенту самому выбрать контракт.
- Спецификация фиксирует границы релиза, сущности/инварианты, API, права и тарифы,
  потоки/состояния, ошибки, сроки/отзыв, миграции/совместимость и критерии приёмки.
  Явно отделять решение лида, требование владельца и открытый продуктовый вопрос.
- У каждой постановки есть версия/commit спецификации, разрешённые пути, запретные
  пути, зависимости, конкретный результат и проверяемый критерий готовности.
  Пробел или несовместимость контракта агент возвращает лиду; не изобретает свой API.
- Общие proto/SQL/generated/interfaces принадлежат одному агенту. Сначала фиксируем
  их и проверяем соответствие ADR, затем запускаем зависимых потребителей параллельно.
- Лид контролирует сообщения, блокеры, diff и evidence; сам сверяет готовность всего
  сценария, а не принимает «готово» каждого пакета за готовность продукта. В текущих
  security-фичах обязательно проверить сквозные обходы, а не только новый endpoint.

### Агенты, изоляция и стоимость

- Только Codex. Кодеры — последний доступный SOL (сейчас gpt-6.1-sol); архитектурные
  решения и сложные разборы остаются у лида. Не запускать Claude/claude-pool из Codex.
- Для механического прогона заранее указанных тестов, документации, проверки
  артефактов и релизной рутины можно брать более дешёвую доступную Codex-модель.
  Не менять модель молча, если она недоступна. Security/protocol review не заменять
  дешёвым механическим прогоном: нужны независимые рассуждения и доказательства.
- Свежий агент на ограниченную задачу, отдельные worktree/ветка/БД/Redis/порты;
  параллельно не больше четырёх агентов и без двух писателей на одни пути.
  Кодовый агент сам делает английские осмысленные коммиты; лид не правит за него
  незавершённую ветку. Собственный ADR/спецификация — ответственность лида.
- Отчёт ≤15 строк: результат, файлы/commit, выполненные команды и результаты,
  риски/непроверенное. Один итоговый отчёт на задачу. Checkpoint — только когда
  освобождает зависимую работу или требует решения. Heartbeat не означает успех.
- Для «запусти и контролируй до готовности» использовать supervised orchestration;
  не завершать работу на факте отправки prompt. Полный handoff без наблюдения —
  только если владелец действительно передаёт владение и не просит контролировать.

### Экономия контекста и координации (владелец, 2026-10-01)

- Один операционный координатор на run: он читает/подтверждает inbox и управляет
  workers. Второй лид не дублирует polling, peek и отчёты о каждом heartbeat.
  Координатор ожидает `worker_done,escalation,question`; обязательные heartbeat
  workers по preamble сохраняются. Вопросы и блокеры не игнорировать.
- Постановка обычно 10–20 строк: результат, SHA базы/спеки, разрешённые пути,
  нужные разделы ADR, зависимости, команды приёмки. Не копировать историю чата,
  весь ADR или чужие отчёты. Обязательные docs читать один раз за сессию,
  затем только изменённые/нужные разделы. Логи хранить файлом, выводить итог/ошибки.
- Лид пишет один контракт; исследовательского агента запускать только на конкретную
  неизвестность. Число кодеров определяют независимые задачи, а не свободные слоты.
  Мелкие исправления по ревью объединять для автора в один follow-up; не заводить
  отдельного агента на каждую строку и не перезапускать активных ради экономии.
- Автор проверяет затронутые места; общие lint/integration и среду проверяет один
  назначенный исполнитель на собранной ветке. Это уточняет требование CLAUDE.md
  о полном наборе перед каждым коммитом: обязательные merge/CI gates сохраняются.
  Evidence содержит SHA, команду, среду, результат; повтор — при релевантной правке
  или сбое. Общие ошибки окружения исправлять один раз, не разбирать каждым агентом.
- Ревью запускать на связном интегрированном diff. После исправлений проверять
  дельту и её влияние, подтверждая итоговый SHA; не повторять весь аудит без причины.
  Для security/protocol по-прежнему нужны два независимых ревью.
- Не обещать процент экономии без замера. `tools/usage-stats.py` сейчас считает
  только Claude; его отчёт не отражает затраты Codex и не доказывает их снижение.

### Проверки и ревью

- Агентам разрешено самостоятельно запускать тесты затронутых мест: прежнее правило
  «все прогоны делает владелец через GLM» для Codex больше не применяется.
- В разработке — typecheck/lint/unit по затронутому слою и целевой integration/race
  по риску. Прогонщик получает SHA, команды/фильтры, ожидаемый результат и отдельную
  среду. Сохраняет фактические результаты; skipped/unavailable не означает passed.
- Не гонять полную регрессию интерфейса или полный набор после каждой правки.
  Обязательные CI-проверки не отменяются; полный server integration — один раз
  перед merge, повтор только если изменение/сбой обесценили прошлый результат.
- Lint запускать через `make lint` **из корня репозитория**: цель сама переходит
  в apps/server, использует корневой config и integration tags, затем pnpm lint.
  Это исправляет устаревшее указание CLAUDE.md: apps/server/Makefile отсутствует.
  После proto/SQL генерации проверить
  drift и включить generated в commit. Версии инструментов сверять с CI.
- Visual suites остаются выключены до отдельного указания владельца. Для новой
  разметки — один ручной QA-проход скриншотами затронутых экранов, не всего приложения.
  Медиа/рендеринг требуют профильных проверок из docs/02 и docs/14, когда затронуты.
- Одно независимое ревью изменения; для auth/прав/токенов/секретов/proto — два.
  Blocker/major исправляются до merge; minor записываются в профильный backlog.
  Финальный review должен относиться к итоговому SHA, а не старому diff.

### Лид принимает готовность, релизный агент выпускает

- До выпуска лид проверяет: scope завершён, ADR соответствует коду, checks и reviews
  на точном commit зелёные, нет blocker/major, известные ограничения честно описаны.
  После push main дождаться CI; красный CI блокирует следующую интеграцию и релиз.
- По поручению на релиз отдельный агент может выполнить подготовку, сборку,
  публикацию/обновление и **анонс через бота**. Лид передаёт версию, точный commit,
  разрешённое окружение, результаты приёмки и обязательные шаги runbook. Не заменять
  выпуск произвольным набором команд без контроля пропущенных шагов.
- Обязательное evidence: changelog именно релизного commit, статистика затрат,
  версия/tag/SHA, CI и release jobs, опубликованный GitHub Release, update feeds и
  доступные установщики/checksums, API/web deployment/version и целевой smoke,
  результат сообщения бота. Выбор шагов учитывает актуальный способ развёртывания
  (images/deployment workflow или разрешённый runbook), не деплоить оба бесконтрольно.
- Перед тяжёлой сборкой проверить диск; локальный electron-builder dist убрать
  после проверки. Не затрагивать чужую GPU-задачу/порты на стенде; секреты не печатать.
- Анонс — обязательное завершение релиза: `tools/release-announce.py <version>`
  из CHANGELOG релизного commit, адрес/токен из dotenv, только точная версия.
  Можно выполнить отдельный `STEPS=announce VERSION=<version> ...release.sh <commit>`
  после проверки опубликованной версии. Не использовать `--all`/`--purge` для
  обычного релиза и не создавать нового бота вместо проверки существующего.
- `nonce=release-<version>` делает повтор идемпотентным. Записать posted/updated/
  unchanged и message id; по возможности прочитать сообщение обратно. Отсутствие
  токена/прав, skipped, ошибка HTTP или непроверенная доставка — **незавершённый анонс**,
  а не успешный конец выпуска. Не объявлять «всё выпущено», пока это не устранено
  либо явно обозначено владельцу как оставшийся блокер.
- Финальный отчёт релиза краткий: версия/commit, что выпущено, проверено, ссылка на
  Release, статус доставки анонса, реальные ограничения. Лид отвечает за этот итог,
  даже если сборку и публикацию делал другой агент.
